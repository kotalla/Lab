## ЛР1. Инфраструктура тестирования и первые тесты

### Что сделано
Настроено рабочее место тестировщика с использованием менеджера зависимостей uv и фреймворка pytest. Для модуля pricing.py написан набор из 12 модульных тестов, проверяющих валидацию позиций заказа (R-02, R-03), расчет скидок по карте, оптовых и промокодов (R-06–R-10), а также логику доставки (R-11). Настроен CI-воркфайл .github/workflows/ci.yml, который на каждый push устанавливает uv, прогоняет тесты с измерением покрытия и исключает UI-проверки из-за отсутствия браузера в раннере.

### Покрытие
Итог прогона `uv run pytest tests/unit --cov=bookshop.pricing --cov-report=term` показал 100% покрытия строк и ветвей. Тесты на дефекты помечены маркером xfail, что позволяет сохранять общий набор зеленым при наличии багов в pricing.py. Измерение ветвей показало, что проверены все условия циклов валидации позиций заказа.

### Найденные дефекты
Выявлено 5 критических дефектов в реализации pricing.py, на каждый заведен issue и написан тест с xfail:
#1 — MAX_QTY не включен в диапазон qty (строка 77, ошибка range).
#2 — promo_applies возвращает bool вместо ожидаемого процента скидки.
#3 — discount_percent не ограничивает итоговый процент лимитом MAX_DISCOUNT.
#4 — discount_amount падает с TypeError при передаче float вместо Decimal.
#5 — calculate не может обработать валидный заказ qty=MAX_QTY из-за ошибки в check_lines.

## ЛР2. Тест-дизайн и тестовая документация

Тест-дизайн Для требований R-02...R-12 применены техники EP, BVA, DT, ST. В docs/test-design.md выписаны классы для qty и сумм. Таблица решений учитывает потолок скидки 25%. Диаграмма состояний Mermaid покрывает все 6 статусов заказа и запрещенные переходы. 
Найденные дефекты Дефект #6 (BVA): диапазон qty не включает верхнюю границу (10). Дефект #7 (DT): скидка 30% не ограничивается 25%. Найдено через анализ таблицы решений. Severity Major, Priority P1. ### Что автоматизировано Все 20+ тест-кейсов из YAML параметризованы в test_design.py через @pytest.mark.tc. Property-based тест проверяет инвариант суммы (R-12) на 200 наборах с derandomize=True. ### Выводы Техника DT оказалась самой сильной: она выявила ошибку с потолком скидки, которую пропустили тесты «из головы» в ЛР1. Документация в YAML позволяет четко отслеживать покрытие требований.

## ЛР3. Функциональное тестирование API и UI

### API-тесты
Для API созданы независимые тесты pytest с клиентом приложения. Проверяются успешные запросы, ошибки валидации, коды ответов, содержимое JSON и побочные эффекты при оформлении заказа.

### Контракт и Schemathesis
OpenAPI-контракт проверяется Schemathesis с воспроизводимой генерацией данных. Исключённые операции перечислены и обоснованы найденными дефектами или особенностями текущего API.

### UI-тесты
Пользовательские сценарии проверяются Playwright. Локаторы и действия вынесены в Page Object-классы; ожидания выполняются через expect, без искусственных задержек.

### Найденные дефекты
Найденные проблемы описаны отдельными GitHub Issues с шагами воспроизведения, ожидаемым и фактическим результатами, severity и priority.

### Выводы
В работе проверены API-контракт, REST-сценарии и пользовательский интерфейс. Page Object отделяет локаторы от сценариев и упрощает поддержку UI-тестов.
